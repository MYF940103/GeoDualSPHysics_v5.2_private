# Private normal-Taylor GPU build recipes

Author-only support/c08_fs_normal_gpu_r1_build.py has independent debug and release actions, each requiring --execution-authorized after root full-read. No build or program invocation occurred during authoring. The separate support/c08_fs_normal_gpu_r1.cpp remains owned by its author and is read/stat-bound only when root executes debug after both files are ready.

Both actions adopt the sealed outputs/c08_fs_normal_taylor_r1_source/source.json and source.zip; neither regenerates sources nor reads instrumented current public GPU code. The preparation proves exactly two logical file differences from the original schema2 archive (JSphCpu.cpp and JSphGpu_ker.cu), exact textual inverse recovery, and all other archived bytes identical. Every prepared file is stat-bound before and after build. In particular the candidate GPU TU includes that archive's original JSphGpu_mdbc_ker.cuh: no centroid or printf modifications are adopted. Release compiles only the GPU candidate; its CPU object stays original.

Original authoritative inputs are logs/c08_preload_schema2_{Debug,Release}_r1.build.json, their owned actual MSBuild calls/logs, and their c08_schema2_build_r1 configuration intermediates. There is no CUDA command tlog in these trees: the one actual JSphGpu_ker.cu NVCC argv is parsed from the corresponding successful MSBuild log, while CUDA read/write, CL command, link command, and resolved-library read tlogs are bound explicitly. Original link recipes must each contain 113 unique objects in that original intermediate directory, including one original main.obj and one original JSphGpu_ker.cu.obj. A print-only or other private object's directory cannot satisfy that closure.

Library paths come from the original resolved link read tlog. Build receipts bind candidate and original captures/archives, private TU/mDBC include, object closure, headers through the complete frozen source file entries, actual tool/log/tlog inputs, copied runtime, helper/note/entry parents, and actual compile/link calls via matrix.invoke. Both retain physical_acceptance=false and record zero help, fixture, solver, memcheck, and native invocations.
