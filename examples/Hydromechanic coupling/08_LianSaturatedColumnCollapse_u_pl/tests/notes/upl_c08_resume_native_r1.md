# r2 GPU certified elastic PRE -> r3 psi0 receiver native profile

Author-only new files: `support/upl_c08_resume_native_r1.cpp`, `_build.py`, `_run.py`, and this note. Nothing is built, decoded or solved by authoring them. The old r2 PRE/runtime/results and previous readers remain unchanged. This is a bounded dedicated elastic-state handoff audit, not general PART/plastic restart or physical collapse acceptance.

## Input/clock/output contract

- C++ CLI: `reader.exe --read GPU DATA PRE EXPECTED_GLOBAL_END FRESHOUT`. Only psi0 and global end4040000 (40000 new updates) or5200000 (1200000 new updates) are admitted; dt2.5us, source event4000000/time10. The material is cp5000/cr1000/eta5/phi25/psi0/sf0; no other groups are implicitly added.
- Load exactly the actual supplied PRE once, using its standard Part filename, current `JGravityPreloadState` and its saved contract. Require legacy material version1/typedMR1, complete unreleased certified elastic schema1, all7060 IDs, κ0 and the original saturated state/22-array/clock checks. The reader checks the PRE against its saved contract; the actual solver separately enforces this contract against its fresh target geometry/normals/P0. No claim that reader self-check alone proves target identity.
- Target `Run.csv` must be a completed actual run with expected **global** Steps, original registry7060/2060/5000 and no ordinary exclusions. Actual PartFiles plus contiguous native enumeration determine frame count. A0.1s run is expected to save10.01..10.10, and3s approximately300 post states; neither count is fabricated or forced by this reader.
- Every target frame is phase1, current6800 IDs: only original fixed1800..2059 are absent; all5000 soil IDs and1800 retained fixed IDs persist without renumbering. Typed output metadata must be MaterialLawVersion2, sf0, no old MaterialReturn key, Model1/Ck2, free seepage, event/actual release completed4000000 and actual source time, damping/Shepard off, and actual statefile path. The target cannot acquire a fake source certificate.
- Preserve every actual zero-based savedStep; completedStep=savedStep+1. Continue scalar `+=dt` from certified.Time/CompletedStep and require error<=1e-14. Source time is never rewritten to10 or0. Part0 is the first actual post-release save, never a synthetic PRE/t0. The scalar end and actual steps are reported.

## Native invariants retained

- Exactly22 typed arrays, all finite, double positions/stresses and original float display-stress rounding. Native rho700..3000; κ finite/nonnegative and nondecreasing from the PRE at every ID/saved state. No final nonzeroκ requirement; maxκ and nonzero count are observations.
- All surviving native P0 bits remain those of the PRE, native excess remains float(p-p0), negative pore pressures remain untouched. True saved FS2/3 pressures must be<=0 and each frame must have nonempty FS coverage.
- Single-J n/V/rho/k law and original5e-13 ledger bound, exact J1 k0, float-rho cache bits, fixed position/zero physical velocity/zeroκ/theta and zero derived markers remain. Only the declared260 fixed IDs retire. No source field or native metadata is overwritten.
- Every saved interval, including receiver Part0, is nonempty and has finite **signed** dterror<=1e-14. This preserves the existing combined natural/pore necessary-step check, not an absolute-value test or new sufficient stability claim. No extra5Pa A/B, half, theory, stress-uniformity or physical equilibrium gate is introduced.

New exports are `typed22.bin` (honest12-byte6800/22/actualframes header, each record actualtime then22 ID-sorted arrays), `typed22_layout.csv`, `clocks.csv`, `history.csv`, and `completion.json`. History displacement is explicitly relative to the imported PRE material positions, not zero-gravity original geometry; it records pressure/excess, velocity, total stress, κ/J/n/k ranges without fitting a reference. The PRE itself is not inserted into the target export.

## One build and one reader owner

- `_build.py --execution-authorized` consumes the actual passed `mdbc_partition_DebugCPU_r1` receipt/capture and only six frozen BI4 utility objects: JPartDataBi4, JPartDataHead, JBinaryData, JObject, JException, Functions. It mechanically reuses the passed branches-reader Debug flags (`MSVC14.36`, C++17, Od/MTd/fp:precise, standard wmain CRT entry), archived headers and no JSph object/solver rebuild. Fresh `outputs/upl_c08_resume_native_r1_build/reader.exe`; first failures are retained.
- `_run.py --read GPU DATA PRE GLOBAL_END FRESHOUT --run-check RUNJSON --execution-authorized` starts exactly one already-built reader only after a closed matching solver receipt. It reuses the consumed mDBC component Win32/Popen invocation utility, refuses existing output/call/check artifacts and active duplicate reader, captures actual exits before checking completion, and never starts or reruns a solver/GenCase.
- Minimal solver receipt, coordinated with the actual owner: passed=true, actual_exit=actual_Win32_exit=0, actual_steps=expected global end, saved_frames=actual PartFiles, and stat entries program/source_build/source_pre_file/**input_xml**. The last item is the actual executed GenCase-generated XML, not a root Def. The runner binds it and checks psi0 material, model, dt/output/event/sourcePRE because the native output has no full psi/cohesion parameter metadata. Solver program/capture must match the closed r3 build. It stat-binds only this PRE/head and current target files, never decodes the old1001 frames or performs a SHA sweep.
- Intended short tag from owner is `upl_c08_resume_r1_psi0_GPU_short`, run receipt `logs/<tag>.run.json`, raw `outputs/<tag>/data`. A suitable separate native result is `outputs/<tag>_native_r1`; full uses the analogous `..._full` tag. The wrapper does not fabricate those owner receipts or choose/launch the physical jobs.

The original legacyPRE metadata is accepted because the explicit loader supports and tests this elastic-only compatibility. Post-plastic r2 data or a failed partially committed GPU stage is not an eligible source. A successful0.1s window cannot be resumed with the ordinary PART loader; any later3s job must follow the separately reviewed elastic-PRE start or remain the same original live process. No automatic next job, retry, event change, physical release or server-package rewrite is present.
