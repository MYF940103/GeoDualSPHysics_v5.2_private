# C08 u-pl shifting compatibility audit

Read-only current CPU/GPU source, local primary MD/PDF and retained XML audit. New name checked absent and exact git ls-files empty. Only this note is new: no guard/source/input/helper edit, build, solver, native decode, new numerical probe or SHA scan. Shifting is a plausible particle-disorder treatment, but current generic shifting is not an already qualified u-pl option or a neutral way to increase AS.

## Current admission and defaults

`JSph.cpp:857-873` accepts modes0=off,1=NoBound,2=NoFixed,3=Full; enabled defaults are ShiftCoef=-2 and **ShiftTFS=0**. Coef0 disables the mode. A separate `<special><shifting>` form supports zones (`1339-1346`, `JSphShifting.cpp:164-199`); duplicate old/new definitions are rejected and mode0's object is deleted. CPU/GPU use the resulting mode/object, not merely whether the XML key exists.
The C08 gravity-container predicate requires `!Shifting` (`JSph.cpp:3813`); its gravity/shared-source admission consequently fails when shifting is enabled (`621-636`). The CPU/GPU observer checks also reject it directly (`JSphCpu.cpp:3110`, `JSphGpu.cpp:1774`). Independent SPR/HG scopes reject it too, but they are not the principal C08 barrier. Changing only the root XML cannot enable a supported combination; a generic CLI override does not bypass these later checks.
Actual r5 XML line174, actual u-pw retrogressive failure XML122-124, dry Bui2021 failure XML109-111 and the inspected granular-column formal inputs all have Shifting0. Their retained ShiftCoef=-2/ShiftTFS1.5 entries are dormant values, not evidence of an enabled/validated coupled shifting run.

## What is actually calculated and applied

- CPU neighbour accumulation is `JSphCpu.cpp:2510-2517`; GPU `JSphGpu_ker.cu:2023-2030`. It forms gradC=sum_j(m_j/rho_j)grad_i W and Dpos=-sum_j(m_j/rho_j)(x_i-x_j).grad_i W in shiftposfs.xyz/w. Modes1/2 cancel the **entire vector** if an eligible boundary/fixed neighbour occurs inside kernel support. For all-fixed C08 these modes have the same wall exclusion effect. Inactive dynamic walls are skipped before the shift block (GPU1806-1811); fixed retained bed samples are still ordinary fixed neighbours when active.
- `JSphShifting.cpp:388-417` and GPU `_ker.cu:123-149` compute delta_x=dt*ShiftCoef*h*|v|*gradC times an optional scalar factor. If ShiftTFS!=0, the factor is0 below the threshold and (Dpos-ShiftTFS)/(dim-ShiftTFS) otherwise. There is no FSNormal projection, no FSType/umbrella/near-FS input, and no upper clamp on that scalar factor. ShiftTFS0 bypasses this surface correction entirely; it does not mean surface shifting is disabled. With 2D threshold1.5 and Dpos1.7, for example, the scalar factor is.4 and a normal component can remain.
- The displacement cap is **per component**, |delta_x_alpha|<=0.1dp, not a vector-norm cap (CPU412-414; GPU144-146). At C08 dp=.04m this means4mm per component and up to5.66mm in2D; nominal first-row centre clearance is20mm. These are allowed worst-case caps, not measured shifts. h=.048m gives8.33%h per component. The velocity factor makes this mechanism vanish as |v| tends to0; it cannot be assumed to rearrange an already arrested region.
- Both Singles call RunShifting at predictor and corrector force stages (CPU905/916; GPU815/826), but their actual Symplectic predictor integrators use **shift=false** (CPU3419; GPU1621). Thus predictor shift is calculated then discarded; the corrector's shift is added to the physical displacement (CPU3660-3663; GPU Simple599-603). Old Verlet also adds delta_x only to displacement (CPU2992-2995; GPU Simple177-181); its existence does not qualify dynamic u-pl Verlet, which remains outside the current admission.
- The shifting class reads only position/velocity for selection/scaling and writes the temporary displacement. There is **no accompanying shifted-field transport** of velocity, p, P0, sigma, kappa or J in these calls. CPU velocity/stress/material return are formed independently at3623-3639; GPU Simple578-580/615-623. There is no delta_x/dt correction to physical velocity or a Taylor update of those state fields after the move.

## Single-J and material-reference implications

For a current fluid particle, legacy m0/rho_mix(J) is not the authoritative quadrature V0J:

    (m0/rho_mix)/(V0J) = rho0/[rho0 + rho_w*(J-1)].

For illustration, J=1.04 gives about.981 and J=.96 about1.020 with C08 densities. The shift concentration/mask therefore differs from the u-pl FS/moment volume even before deciding how to transport fields. This is a concrete implementation gap, not a claim that a two-percent volume-weight difference alone caused the pressure pulses.
J is advanced from **physical** force-stage theta only (CPU3303/3318; GPU porosity update); the independent pressure and material updates contain no shift term. Derived n=1-(1-n0)/J, rho=rho_w+(rho0-rho_w)/J and k(J) can consequently remain algebraically exact after position-only shifting. Passing that ledger does not prove that relocated particle geometry, solid-volume conservation and pore-fluid storage/flux still represent the same material deformation.
Retaining fields by ID while moving x is the existing approximate position-regularization policy. If instead interpreted as remeshing a fixed Eulerian field, the missing first-order change is grad(f).delta_x. At hydrostatic slope gamma_w, a4mm vertical numerical move corresponds to39.23Pa; this is an analytic scale, not a measured C08 error. Strong p/sigma/kappa gradients can be much more sensitive. A consistent remesh cannot just correct p alone: J, velocity, sigma, kappa and the material P0/reference interpretation must be considered together. Naively Taylor-remapping kappa/P0 may violate their current material-ID nondecrease/bit invariants; that requires an explicit representation decision, not weakening the existing native guards.

## Free surface, contact and PRE/release

The shift Dpos is not the current J-weighted FSType classification. A positive ShiftTFS therefore cannot guarantee zero normal movement for all true FS2/3, nor protect a finite near-surface halo. Scalar suppression freezes some surface points while nearby active points move differently; raw shifting on truncated support can move surface particles into empty space. Both differential movement and genuine dilation can produce sparse bands/gaps; the present completed snapshots do not prove which occurred, and current r5 has shifting OFF.
Fixed points are outside RunShifting's Np-Npb range, so the five kept bed IDs/normals/slip roles are not themselves shifted. If shifting were admitted, it would change fluid neighbours of those samples and the MLS/FS stencil after each divide; modes1/2 would suppress fluid shifting near them, whereas mode3 would not. NoPen is not a free-surface fix. CPU applies the lower-plane projection after adding the shift (3684-3686); GPU projects the kernel displacement at host1718-1721, after the shift was added. `FunFixedPlaneContact.h:12-19` clips the combined trial position and, if incoming, normal velocity. Using that clip to repair a numerical shift can alter physical contact response while the existing same-stage reaction-to-J/Darcy closure remains absent.
The retained certified PRE was produced without shifting. Its contract currently omits a shifting policy because admission forbids one; this omission is not permission to change the PRE operator. Any eventual test must keep source/pre-release paths literal and activate only after the certified receiver's release, with separate operator metadata. Ordinary PART restart, source certification and the present AS05 program/helper are not to be repurposed or modified. Position-only regularization also enters recorded material-ID displacements; such shifts cannot silently be called purely physical settlement/runout.

## Primary evidence and the smallest defensible next route

The local `GeoDualSPHysics.pdf`, page5, section2.5.3/Eqs21-23 (MD259-279), documents the retained scalar-threshold scheme and explicitly notes its simplified surface freezing can underperform consistent surface correction; it identifies conservative/ALE and volume-conserving shifting as further improvements. It is evidence of usefulness in cohesive granular simulations, not current finite-J pressure/history transport validation.
Local `Feng 2024_CMAME.pdf`, printed10-11, section3.2.3/Eqs30-37 (MD573-643), describes velocity-scaled shifting, tangent projection on free-surface **and vicinity** particles, and no shift for external particles with too few neighbours. Its 0.1dp maximum and Cshift2 are specified; its extension-to3D is explicitly untested there. MD1256-1264 also notes that physical expansion can leave sparse distributions even with shifting. Lian2023 local text does not specify this OPS variant as a ready C08 switch. None of these references proves a direct transplantation into the present dynamic J/p/DP/NoPen solver.

1. **Do not unlock the present flag yet.** The minimum next component is a frozen-geometry shift proposal on already saved states: compute the candidate delta_x using V0J, report delta_x/h, normal movement/gaps, support improvement and constant/affine-field transport defects. No positions/state in retained data are changed. An initial complete-stencil interior-only subset, with true FS plus a support halo and wall-adjacent particles frozen, avoids pretending a scalar ShiftTFS is a no-gap condition. This is a displacement/transport component, not another long physical run.
2. If that displacement has useful measurable benefit, a bounded CPU/GPU zero-step stage component should verify identical constant fields, keep-bed/fixed geometry, no plane crossing, valid J/ledger and the declared handling of nonconstant p/J/sigma/kappa/P0. Decide explicitly whether the first spatial diagnostic is approximate position-only regularization or a consistently transported state. A full general ALE framework is not a prerequisite to measure a narrow candidate, but position-only must not be relabelled as conservative u-pl transport.
3. Near-surface extension should use the actual current geometry/mask plus a halo and a tangent projector (I-nn^T) rather than simply ShiftTFS0/full mode; isolated weak-support points should not be forced to move. Its displacement limit must be stated as vector or component limit. Contact constraints should bound the numerical displacement separately or exclude the wall strip, rather than rely on the physical NoPen velocity projection to absorb it. This remains candidate development, not a guard-only patch.
4. Only after those specific component results should an explicitly labelled release-only short physical comparison be considered, with AS unchanged to isolate shifting, separate numerical displacement telemetry and the original pressure/FS/clock/ID/material safeguards. It must inspect gaps and pressure/storage as well as visual particle regularity. No such run or production change is authorized or performed by this note.

Conclusion: shifting is a reasonable line of investigation for clustering, but current u-pl rejection protects concrete quadrature, transport and surface/contact gaps. The smallest safe progress is a qualified displacement/field-transport component, not enabling the existing XML mode or jointly increasing AS and shifting until the picture looks regular.
