# C08 positive ponding: full-step policy and a stagewise candidate

Read-only current CPU/GPU source and local primary-text audit. New name checked absent and exact git ls-files empty. Only this note is added; no production/helper/input edits, build, solver or native decode. The frozen AS05 reader/program dependencies remain unchanged. The reported trace example is ID4959, FS2 with half-stage p about+381726 Pa; this audit does not calculate another trace or attribute the full instability to that value alone.

## Why the positive half pressure reaches the corrector

1. CPU `JSphCpuSingle.cpp:903-920`, GPU `JSphGpuSingle.cpp:813-830`: force(n) -> Pre -> half `RunCellDivide` -> force(half) -> Corr. Pre stores p_n in PorePressPre and forms p_h=float(p_n+dt/2*rate_n) (`JSphCpu.cpp:3431-3439,3347-3357`; GPU `JSphGpu.cpp:1629-1648`). The corresponding J/velocity/stress half state is advanced separately.
2. The half divide sorts p and p_n with all primary arrays, then calls `ApplyPorePressureBoundaries` (CPU Single617; GPU Single581). That function refreshes wall state -> native FS/C -> wall C, but **positive-only ponding requires !PorePressPre** (CPU1633-1641; GPU1297-1311). At this point the saved p_n buffer exists, so it explicitly skips ponding. No alias or missing pointer reset is needed to explain this behaviour.
3. The corrector force again refreshes same-geometry wall state/FS/C (CPU Single695-697, CPU1170-1210; GPU Single631-633, GPU1202-1212). Its call named `ApplyFreeSurfacePorePressure` is the **legacy drainage** path (CPU1443-1456; GPU1233-1236), not the free-seepage positive-only call. C08 has legacy drain=false: CPU returns, GPU invokes the wrapper with ponding=false and drainfs=false. It therefore leaves positive p_h unchanged even when the force's own classification is FS2/3.
4. AS preparation follows (CPU Single703-704; GPU Single635-639), then mechanical force/AV, completed Ace/wall Ace and dynamic Darcy. Darcy consumes that same force-stage FSType and p_h; FS2/3 selects its raw hydraulic branch (`JSphGpu_ker.cu:1581-1596`, CPU3251-3260). The positive half value can thus affect both momentum/AS/Ace and the corrector pressure RHS. This is not simply a classification lag.
5. Corr uses p_n+dt*rate_half, **not p_h+dt*rate_half** (CPU3373-3375,3724; GPU1726-1728), then frees PorePressPre (CPU3731; GPU1741). The main loop performs completed-geometry divide before time/save (CPU Single1399-1410; GPU1234-1245), so the now-null Pre pointer permits completed-state ponding. Saved FS2/3 can obey p<=0 while an earlier force has consumed p_h>0.

The positive-only kernel/loop affects only normal native fluid FS2/3 with finite p>0 (GPU ker1104-1105; CPU1639-1640). It preserves p<=0, NaN/Inf for the existing finite validator, P0, rate, effective sigma, J/theta and kappa. It is not the legacy p=0 AND rate=0 drainage path, and not a negative-pressure cut-off.

## What the primary boundary text does and does not establish

- Local `src/papers/PDF/Lian 2021 seepage flow unsaturated porous media.pdf`, printed21 Eq71, defines pressure head h_w<=0 on the open free-seepage boundary. Printed22 explicitly describes scanning after each completed time step: positive head is reset to0; otherwise evolution continues. Eq72 separately removes the inappropriate Taylor-defect correction at a truncated surface. The existing completed-only split follows that stated timing; the text does not demonstrate a two-stage projected Symplectic method.
- Local `src/papers/u-pw/Lian 2023 u-pl.md:881-889` (PDF printed19, section4.4) adopts the earlier free-seepage treatment and p_l<=0, and uses its semi-implicit scheme. It does not specify the admissibility of an explicit predictor's pressure or provide this code's projected explicit-stage algorithm. Thus current full-only behaviour is consistent with the declared policy and earlier end-step wording, but it does not enforce the inequality at every RHS evaluation.
- Section3.5.3 Eq47 addresses the growth of **negative** pressure associated with plastic dilation in a different temporal treatment. It neither supplies a positive-pressure drainage condition nor justifies clearing negative pressure in this candidate. A negative FS2/3 pressure remains allowed under the current chosen ponding policy.

## Lowest-cost isolated candidate, not an accepted replacement

For a separately labelled, released bounded gravity-handoff candidate only, ensure the current force's **already classified** normal native FS2/3 has finite positive p set to0 immediately before AS/force. Use the same finite predicate, existing wrapper (GPU rate=NULL, ponding=true) or CPU loop; no new mask, FS threshold, negative clamp, array or rate reset. Scope it to the existing dynamic/feedback/free-seepage gravity receiver **after release**. Keep completed-state ponding and every original full-step check.

Exact insertion neighbourhoods: CPU Single after line703 legacy boundary call and before704 AS; GPU Single after636 and before639 AS. CPU has no C08 external top load, so its earlier698 load call adds no complication here. Do not broaden this candidate to loaded/Cryer, periodic, general restart or an elastic source.
**Required wall consistency:** force tracking has already fitted wall p before this prospective projection (`Cpu1172`, `Gpu1204`). Refresh `ComputeDynamicPoreWallStateCpu/Gpu` after the projection and before AS/force so adjacent walls read the projected native p. Native FS/C and wall C depend on unchanged geometry/J, not pressure, so a new FS/C neighbour pass is unnecessary for this pressure-only change. Preserve the same FSType through the force/Darcy call; do not substitute an old full-step mask. This adds a wall-state refresh, not a new mechanical force pass.

Do not merely remove `!PorePressPre` globally from ApplyPorePressureBoundaries: that would also change pre-release/source half steps and the retained PRE trajectory. Also do not write into PorePressPre during the half-force projection: p_n must remain the corrector base, not be replaced by projected p_h. A half-divide-only projection would be cheaper and is followed by an existing wall refresh, but needs proof that its mask equals the subsequently recomputed force mask; the force-local location is the unambiguous same-classification control requested here.

## Numerical meaning and minimum evidence if later implemented

- This is a new projected-stage integration policy. Projection is nonlinear and non-smooth at p=0 and at changing FS membership; it can change temporal order, boundary discharge and the coupled spectrum. It does not follow that pressure peaks or growth must improve.
- With finite Kw, p changes without an immediate sigma/J/rate correction. The pressure-storage proxy changes by (n/Kw)*delta-p at frozen n; an internal predictor projection must not be counted automatically as accepted drained water mass. The single-J algebraic ledger cannot certify the flux/storage balance. The next actual Darcy call overwrites rates normally.
- AS uses sigma_eff-pI: removing positive p can increase total tensile eigenvalues and change its nonlinear force. The candidate leaves the AS formula/epsilon/exponent unchanged but does not hold its numerical output fixed. Mechanical and Darcy pressure effects must both be observed.
- First evidence can be the existing scalar finite/nonpositive/negative/nonfinite canaries and a narrowly observed stage path: raw UPDATE2 p_h, the projected force pressure, same-stage FSType, refreshed wall p and subsequent corrector RHS. Verify an inactive/no-positive case preserves the old path and P0/J/sigma/rate are not accidentally changed by projection. Preserve the original native/clock/keep/plane/finite guards. No new solver, half chain or threshold is authorized by this note.
- Record this force-stage policy under a new candidate identity/metadata; do not silently relabel completed-only results or reuse frozen AS05 trace/checker receipts as proof of the changed policy. The retained source PRE, its contract and original programs stay intact; release-only scope protects PRE operator identity, not an unmeasured post-release physical equivalence.

Conclusion: the current half positive value is explained by an intentional completed-only split, not a demonstrated indexing/FS bug. A same-force-mask positive projection is a small, testable boundary-time consistency candidate with explicit wall and storage implications; it is not yet a physical fix or a production merge decision.
